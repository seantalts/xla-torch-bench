# XLA:CPU vs PyTorch Inductor — perf-win opportunities

Source: ranked analysis off the 2026-06-02 benchmark run in [README.md](../README.md). 12 opportunities ranked by `(payoff × confidence) / effort`.

## Summary

Two big aggregate patterns. **(1) XLA loses f32 GEMM hard** (`dot_small` 0.31x, `dot_medium` 0.43x, `dot_transpose` 0.44x). On bf16 Inductor face-plants into a scalar fallback (`dot_medium` 469x, `gpt2_block` 183x, `mlp_mixer` 175x — out of scope), but the *f32* GEMM gap is real and cascades into every transformer-block benchmark. **(2) XLA loses reductions across the board, and bf16 reductions especially** (`sum_axis` bf16 0.28x vs f32 0.71x; `mean_axis` bf16 0.34x vs f32 0.84x; `layer_norm` at 4096 drops to 0.28x f32 — way worse than `rms_norm` at the same shape). The bf16-reduction collapse is almost certainly an upcast-to-f32-then-reduce-then-downcast scalar loop with no native bf16 vector accumulator. Where XLA wins on f32 it's small/medium pointwise (`silu_mul`, `add_chain` 1024, `rms_norm` 1024); the elementwise tail-handling story (`add_mul_aligned_vs_misaligned` 1025 = 0.71x) is still leaking 15–30% on misaligned trailing dims even after the xtile-aligned-ops work.

The high-leverage targets cluster around: f32 GEMM micro-kernel / oneDNN dispatch, bf16 reduction codegen, two-pass-mean-variance fusion, GEMM-epilogue (bias / activation / residual) fusion, and finishing the misaligned-tail vector emitter.

## Ranked opportunities

### 1. bf16 reductions: stop upcast→scalar-loop→downcast, emit a vectorized bf16 accumulator
**Gap.** `sum_axis (1,4096,1024) bf16` = 0.28x; `sum_axis (1,1024,4096) bf16` = 0.31x; `mean_axis` same shapes 0.34x and 0.38x. Compare to the f32 rows of the same benchmarks (0.71–0.95x): the bf16 path is ~2–3x slower than f32 for the *same shape and same op*, which is backwards (bf16 has 2x the memory bandwidth).

**Why it's slow.** Almost certainly the bf16 reduction is being decomposed as `convert_bf16→f32`, scalar f32 reduction, `convert_f32→bf16`. The `convert` ops likely block vector dialect lowering, or are vectorized but the reduction itself drops to scalar because XLA's vector reduction emitter doesn't have a bf16 path. PyTorch with the same shape is roughly memory-bound; XLA at 3x slower is clearly not.

**What to try.** Dump the LLVM IR (or vector dialect) for `mean_axis bf16` at `(1,4096,1024)` and confirm. If the reduction is scalar, teach the CPU reduction emitter to keep a `vector<Nxf32>` accumulator while loading `vector<Nxbf16>` and widening on the fly (BF16-DP-style accumulator pattern: `fma(widen(bf16_vec), 1.0, f32_acc)`). On NEON without BF16 extensions you still want a vectorized widen-then-fma. The fact that *every* bf16 reduction row is broken suggests one fix lights up many benchmarks.

**Effort: S–M.** Localized to reduction emitter; the f32 version already works.
**Payoff: high.** Fixes ~6 rows directly (every `*_axis bf16`, `softmax bf16`, `layer_norm bf16`) and is on the critical path for any bf16 transformer activation.
**Confidence: high** that the diagnosis (decomposed scalar bf16 reduction) is the right one; the f32/bf16 ratio is the smoking gun.

### 2. f32 GEMM micro-kernel — XLA is leaving ~2–3x on every f32 matmul
**Gap.** `dot_small (256³) f32` = 0.31x, `dot_medium (1024³) f32` = 0.43x, `dot_transpose (512,768,512) f32` = 0.44x. These are not edge cases — they're the dominant cost in every transformer block (`gpt2_block f32` 0.58–0.74x, `mlp_mixer f32` 0.86x, `mha_block f32` 0.40–0.49x).

**Why it's slow.** Two suspects: (a) XLA:CPU's f32 dot dispatch is not hitting oneDNN / Eigen contraction for these sizes — possibly going through a custom emitter path that's missing pack/unpack of the rhs; (b) the GEMM is dispatched but the micro-kernel choice is wrong for these tile sizes (M=K=N=256 is small enough that pack overhead dominates if not skipped, and 1024×1024×1024 should be near roofline). PyTorch goes straight to oneDNN's `sgemm`.

**What to try.** First confirm dispatch: `XLA_FLAGS=--xla_dump_to=...` and check whether the HLO `dot` is being emitter-codegen'd or dispatched to a custom-call (oneDNN). If emitter-codegen, force oneDNN dispatch for these shapes (`--xla_cpu_use_thunk_runtime=true` plus the oneDNN matmul flag, whichever is current). If oneDNN is dispatched but slow, check the LHS/RHS packing path — for transposed RHS (`dot_transpose`) we may be doing an extra copy. For small (256³), the answer is probably to skip packing entirely and use a register-tiled inline kernel.

**Effort: M** if it's a dispatch / heuristic fix; **L** if XLA's own GEMM emitter needs work.
**Payoff: high.** Every transformer benchmark inherits this.
**Confidence: high** that the gap exists; **medium** on whether it's a dispatch heuristic vs an actual kernel quality issue without dumping the HLO.

### 3. Two-pass mean/variance in layer_norm — fuse into a single pass
**Gap.** `layer_norm (1,4096,768) f32` = 0.28x and bf16 = 0.29x. The same shape on `rms_norm` is 0.84/0.85x. The delta between layer_norm and rms_norm at the same shape is enormous — and the only structural difference is that layer_norm needs both `mean` and `var = mean((x-mean)^2)`, i.e. a second pass over the row.

**Why it's slow.** The naive HLO is `mean(x); subtract; square; mean; ...` — that materializes `(x - mean)` to memory and reduces it again. PyTorch's `nn.LayerNorm` (or Inductor's lowering of it) uses Welford's online algorithm OR a single-pass `var = mean(x²) - mean(x)²` identity, so it touches `x` once. At 4096×768 the row no longer fits in L1/L2, so the second pass is a full DRAM re-read — which matches the 3.6x slowdown almost exactly (2 passes vs 1, plus elementwise overhead).

**What to try.** Pattern-match `mean((x - mean(x))²)` in HLO and rewrite to `mean(x²) - mean(x)²` (or a two-output fused reduction). XLA already has reduce-fusion logic; the trick is fusing two reductions over the same axis with a shared input. Alternative: a pass that recognizes the variance idiom and emits a custom emitter that keeps `sum_x` and `sum_x²` in registers in one sweep. This is essentially what's needed for any "compute mean+var together" pattern and generalizes to BatchNorm, GroupNorm, online softmax.

**Effort: M.** New rewrite pass + variance emitter; the fusion infrastructure already exists.
**Payoff: high.** ~3x on layer_norm-large directly; lights up every model with LayerNorm (~every transformer). Also reduces gpt2_block and mlp_mixer_block f32 gaps measurably (both contain 2× LN per block).
**Confidence: high.** The rms_norm-vs-layer_norm delta at identical shape is direct evidence that the second pass is the cost.

### 4. Softmax: fuse exp/sub/div with the max-reduction and the sum-reduction (online softmax)
**Gap.** `softmax (1,12,512,512) f32` = 0.75x and bf16 = 0.69x; `softmax (1,16,1024,1024) f32` = 0.74x and bf16 = 0.66x. Constant ~25–35% loss across shape and dtype. This also bleeds into `mha_block f32` and `gpt2_block f32`.

**Why it's slow.** Standard softmax is three passes: `max`, then `exp(x-max).sum`, then `exp(x-max)/sum`. Each pass re-reads the row from DRAM at these sizes (1024-wide softmax rows × 16384 rows = 64MB intermediate). PyTorch likely has a fused 2-pass (or online 1-pass) softmax in its inductor template.

**What to try.** Two options. (a) Implement online softmax in the reduction emitter — combine the max-reduction and the sum-reduction so `exp(x-max_running)` is recomputed once when max updates, but only one pass over `x`. (b) Cheaper: at minimum fuse `subtract(max)` and `exp` into the same loop as the *second* reduction (`sum`), and fuse the final `divide` with the consumer. Confirm via HLO dump whether the three passes are currently materialized.

**Effort: M** for the 2-pass-fused version; **L** for true online softmax.
**Payoff: medium–high.** Direct 30%+ on softmax rows; also helps mha/gpt2 attention. Generalizes to flash-attention-style emitters down the road.
**Confidence: high** that softmax is multi-pass today (this is a well-known XLA pattern); **medium** that closing it gets all the way to parity (could be other secondary issues at these sizes).

### 5. Bias + GELU fusion into the GEMM epilogue (and into the next reduction)
**Gap.** `dot_bias_gelu (1,1024,768) f32` = 1.01x — *barely* parity even though XLA wins on plain GEMM-free pointwise. The bf16 row is a meaningless Inductor blow-up. More tellingly, `gelu_chain f32` = 0.65x — two identity matmuls with a GELU between them; identity matmul is essentially a memcpy, so this is almost entirely GELU + GEMM-launch overhead.

**Why it's slow.** GELU after a GEMM should be a fused epilogue (oneDNN supports `post_ops=eltwise_gelu_tanh`). If XLA dispatches the dot to oneDNN but emits GELU as a separate kernel, you pay (a) write GEMM output to DRAM, (b) read it back, (c) compute GELU, (d) write again. For `dot_bias_gelu` at 768×768 that's ~6MB of round-tripping. Inductor stitches the epilogue into the kernel.

**What to try.** Add (or enable) a pass that pattern-matches `gelu(bias_add(dot(...)))` and either (a) lowers to oneDNN's `dot+post_op` API if dispatching there, or (b) extends XLA's own GEMM emitter to take an epilogue functor. Same hook should accept `relu`, `silu`, `bias_add`, and `add(residual)` — covers MLP-block patterns everywhere.

**Effort: M.** Dispatch-level work + a new fusion-pass rule.
**Payoff: high.** `dot_bias_gelu` should jump, but more importantly the residual-add at the end of GPT-2 / Mixer MLPs is the same pattern; this is on the critical path for every transformer.
**Confidence: medium–high.** Confidence that the gap exists and the cause is unfused epilogues is high; confidence that the fix is straightforward depends on whether XLA already plumbs an epilogue API to its GEMM dispatch.

### 6. Misaligned-tail elementwise — finish the xtile-aligned-ops job
**Gap.** `add_mul_aligned_vs_misaligned`: shape (1,4096,**1024**) = 0.85x, (1,4096,**1023**) = 0.83x, (1,4096,**1025**) = **0.71x**. The d=1025 case (which has a 1-element tail that the alignment-prologue can't absorb) is still leaking measurably. d=1023 is closer to aligned because it's "one short" — the tail of (1024 - 1) handled by the prologue-style mask is apparently cheaper than the trailing-1 case in d=1025.

**Why it's slow** (you know this better than I do). The 1025 case is forcing the emitter into either (a) a scalar 1-element tail after a 1024-element vector body, or (b) a masked vector tail with a poorly chosen mask register / predicate. The d=1023 case can be handled with a single masked vector load.

**What to try.** Audit the emitter output for d=1025 specifically — the asymmetry vs d=1023 is the evidence. Likely fix: emit a final masked vector with mask = `[1,0,0,...,0]` rather than splitting into vector-body + scalar-tail. Alternative: pad-on-load when the tail size is small (< vector width / 2) so the body subsumes the tail.

**Effort: S.** This is in your recent territory.
**Payoff: medium.** Closes ~15% on this specific shape; generalizes to any model with d_model values that aren't multiples of the vector width (vocab sizes, head counts × head dims).
**Confidence: high** that the gap is in the misaligned tail (the three-row sweep was designed to isolate it).

### 7. Repeat / broadcast materialization in GQA — fuse `repeat_interleave` into the consumer
**Gap.** `gqa_block (1,512) f32` = 0.63x and `(1,2048) f32` = 0.72x. The bf16 wins are Inductor failures, ignore. The f32 numbers say there's real XLA-side cost.

**Why it's slow.** `jnp.repeat(k, 4, axis=1)` expands `(b, 8, s, d)` to `(b, 32, s, d)` — 4x memory growth. If XLA materializes the repeated tensor before the `q @ k_full.T` matmul, you pay 4x the K/V memory traffic and the GEMM is fed with a strided/copied input. Ideal lowering: never materialize; broadcast-index inside the matmul, or split into 8 small GEMMs that share the same K block.

**What to try.** Check the HLO: does the `broadcast` (after `repeat`) get fused into the dot, or materialized? If materialized, add a fusion rule: a dot whose LHS or RHS is a broadcast (with the broadcast dim being a non-contracting dim) should consume the unbroadcast input and let the dot emitter handle the stride. Alternative lowering: rewrite GQA into a `jnp.einsum` that exposes the group structure (`"bhqsd,bhksd->bhqsk"` with h_q / h_kv as separate axes) so the broadcast is implicit. This second path is actually the right long-term answer.

**Effort: M.** Either a fusion-pass rule or a GQA-pattern recognizer.
**Payoff: medium–high.** GQA is *the* attention shape in modern LLMs (Llama, Mistral); closing this is on the critical path for any LLM workload. f32 wins here transfer to bf16 once #1 lands.
**Confidence: medium.** Diagnosis is plausible but I haven't confirmed materialization; an HLO dump would settle it.

### 8. mha_block f32 — confirm fused-attention pattern recognition isn't kicking in
**Gap.** `mha_block (1,12,128,64) f32` = 0.41x; `(1,12,512,64) f32` = 0.40x; `(1,12,2048,64) f32` = 0.49x. Constant ~2.5x slowdown across sequence lengths.

**Why it's slow.** Plain SDPA without masking should be the easiest possible attention case. The two GEMMs (Q@Kᵀ and attn@V) are small per-head (128×128, 512×512, 2048×2048) and at HEAD_DIM=64 oneDNN packing overhead dominates. PyTorch probably falls into a hand-tuned SDPA kernel even from `torch.compile`. Additionally the intermediate `attn` matrix (12·s·s) is being materialized — for s=2048 that's 192MB of f32, which exceeds cache.

**What to try.** Two layers. (a) Short-term: tile the per-head GEMMs together (batch the 12 heads into one oneDNN call with batch_size=12 if not already; check the HLO for whether the batch dim is being unrolled). (b) Long-term: a flash-attention-style emitter that tiles q-blocks, runs Q@Kᵀ + softmax + ·V in registers, never materializing the s×s attention matrix. This is the same machinery as opportunity #4 (online softmax) plus a Q-block outer loop.

**Effort: L** for flash-style; **M** for batched-heads + intermediate elimination.
**Payoff: high.** Attention is the entire ballgame for LLM inference. Even partial fixes propagate to gpt2_block.
**Confidence: medium–high.** Confidence that materialized attention matrix at s=2048 is part of the cost is high (192MB is undeniable). Confidence that head-batching is the issue at small s is medium; needs HLO dump.

### 9. Pointwise at "medium" shapes (4096) — investigate why parity flips at the larger size
**Gap.** Same op, two shapes: `rms_norm (1,1024,768) f32` = 1.30x (XLA wins) → `(1,4096,768) f32` = 0.84x (loses). `add_chain f32`: 1.07x at 1024 → 0.70x at 4096. `silu_mul` actually holds (1.23x → 1.17x), so it's not universal.

**Why it's slow.** At 1024 rows the working set fits in L1/L2; at 4096 it doesn't. XLA's emitter might be choosing a tile size that's tuned for L2-resident data and the larger shape is hitting DRAM with bad prefetch / stream patterns. PyTorch may be using OpenMP-parallel split-K (or split-M for normalizations) that XLA isn't matching. Note that `silu_mul` holds across sizes — that's purely pointwise; it's the *reduction* benchmarks (rms_norm, add_chain has none, but interestingly add_chain still degrades — that's 4 inputs × 4096×768×4B = 48MB read traffic, memory-bound).

**What to try.** Compare the threading split between XLA and torch at 4096 — if XLA is splitting on the wrong axis (e.g., parallelizing across rows but with each thread doing a small chunk that doesn't amortize prefetch), tune the parallel-block partitioner. For pointwise-with-reduction (rms_norm), try larger row-blocks per thread or row-blocking with software prefetch. Confirm with `--xla_cpu_parallel_task_assigner_*` flags.

**Effort: S–M.** Tile-size tuning + threading heuristic.
**Payoff: medium.** Closes 15–30% on a class of memory-bound pointwise/normalization at "real activation" sizes; doesn't help GEMM-dominated workloads.
**Confidence: medium.** Diagnosis is hypothetical without a hardware-perf profile; could also be a vectorization issue at 4096-row stride.

### 10. Eliminate `reshape`/`transpose` materialization in transformer blocks
**Gap.** `gpt2_block (1,512,768) f32` = 0.74x and `(1,2048,768) f32` = 0.58x. The big shape's worse-than-the-small-shape pattern suggests memory traffic dominates at 2048.

**Why it's slow.** The block does `(h @ wq).view(b,s,12,64).transpose(1,2)` three times — that's three reshape+transpose pairs feeding three matmuls. Each `transpose` over a non-trivial layout in XLA can materialize a copy. PyTorch's view+transpose is a free metadata change for the same access; downstream oneDNN matmul takes a strided input. XLA may or may not pass strided arguments to its GEMM dispatch.

**What to try.** Inspect the HLO post-layout-assignment: are the transposes being eliminated as layout choices, or materialized as `copy`? If materialized, the fix is in `LayoutAssignment` — choose layouts so the consumer GEMM consumes the producer's natural layout. Failing that, allow the GEMM dispatch to accept strided LHS/RHS (oneDNN supports this). Also worth checking: is the final `.transpose(1,2).reshape(b,s,D)` after `attn @ v` being materialized between attention and the output projection? That's a 12·s·64 → s·768 reshape that should be a no-op.

**Effort: M.** Layout-assignment work is fiddly but well-trod territory.
**Payoff: medium.** Helps gpt2/mlp_mixer; doesn't help pure-GEMM or pure-pointwise benchmarks.
**Confidence: medium.** Plausible but needs HLO inspection to confirm; the gpt2/mha gap is also explained by #2 (GEMM) and #4 (softmax) so attribution is uncertain.

### 11. `add_chain` at 4096×768 f32 — pure-pointwise loses 0.70x at "real activation" size
**Gap.** `add_chain (1,4096,768) f32` = 0.70x. Four inputs, three adds. No reductions. Pure memory-bound. PyTorch hits ~0.39ms, XLA ~0.55ms.

**Why it's slow.** At 4 × 4096 × 768 × 4B = 48MB read, this is bandwidth-bound. PyTorch is presumably fully vectorized and parallel. XLA at 1.4x slower despite identical theoretical bandwidth means either (a) vector width chosen smaller than the hardware supports, (b) thread count / chunk size mismatch, or (c) extra copies in the emitter (e.g., temporaries for `a+b` not in registers).

**What to try.** Dump LLVM IR for this kernel — should be a flat `f32×16` (NEON: ×4) load×4, add×3, store loop with a parallel-for outer. If you see *any* temporary stores between the adds, the SLP vectorizer or the fusion emitter isn't holding intermediates in vector registers. If the loop is clean, it's a threading/chunk-size issue — try larger chunks per thread. Note: contrast with the bf16 row (1.27x — XLA wins) suggests the issue is f32-specific (smaller per-element work, more sensitive to overhead).

**Effort: S.** Localized diagnosis.
**Payoff: low–medium.** Worth fixing but a narrower win than the GEMM/reduction items. Generalizes to any wide-input pointwise (residual adds, RoPE prep).
**Confidence: medium.** The bf16-wins-but-f32-loses asymmetry is suggestive but unusual; could be a compile-options difference between paths.

### 12. Single-axis reduction tile-size tuning (sum_axis, mean_axis)
**Gap.** Even on f32 (where the bf16 catastrophe doesn't apply), `sum_axis (1,4096,1024) f32` = 0.71x and `(1,1024,4096) f32` = 0.82x. The asymmetry between the two shapes is interesting — reducing the *long* (1024-row) dim at 4096-wide is slower than reducing 4096 elements with 1024 rows.

**Why it's slow.** At (1,4096,1024) you have 4096 reductions of length 1024. At (1,1024,4096) you have 1024 reductions of length 4096. The first has more row-parallelism but each row fits in cache once. The second has bigger rows that may need partial tree-reduction. XLA's reduction emitter probably uses the same tile/strategy for both; PyTorch picks per-shape.

**What to try.** Add (or tune) a reduction heuristic that picks (a) vector width × unroll factor × accumulator count based on reduction length, and (b) row-blocking based on cache size. For length-1024 f32 reductions, 4 accumulators × 16-lane × 16-element unroll is roughly right on AVX-512; NEON wants different. Concretely: parameterize the current vector reduction emitter on (vector_width, n_accumulators, row_block) and benchmark a grid.

**Effort: S–M.** Heuristic + autotuning.
**Payoff: medium.** Direct ~20–30% on reductions; compounds with #1 (bf16 reductions); generalizes since reductions are everywhere.
**Confidence: medium.** Reasonable hypothesis; could also be parallelism overhead at these problem sizes.

## Cross-cutting note

Three of the top five items (#1 bf16 reductions, #3 LN variance, #4 softmax) all touch the **reduction emitter**. If there's any shared infrastructure work that would unlock all three — e.g., a fused multi-output reduction primitive that can express `(sum_x, sum_x², max, ...)` over the same row with bf16-vector inputs and f32-vector accumulators — it's worth doing once rather than three times. That single emitter primitive arguably also enables online softmax (#4 long-form) and is the foundation for any future flash-attention work (#8). Worth scoping as a parallel design exercise alongside the targeted fixes above.
